## 1. ملخص تنفيذي

تم إغلاق النظامين الفرعيين **FS-007 — المهام والجداول اليومية** و**FS-008 — نقاط الأسرة والمكافآت** إغلاقاً كاملاً وفق منهجية المشروع المعتمدة: واجهة أمامية (15 شاشة) + طبقة بيانات حقيقية على SQLite (offline-first مع outbox للمزامنة) + عقود Firestore جاهزة للتكرار السحابي + تكامل فعلي مع محركات المراحل السابقة (FS-011 قواعد العائلة عبر الجسور `taskGated` / `rewardUnlocked`) + 26 اختباراً جديداً كلها خضراء + تحليل الكود نظيف (0 أخطاء).

تم اكتشاف وإصلاح **3 ثغرات منطقية حقيقية** أثناء كتابة الاختبارات — وهي ليست إصلاحات شكلية بل مشاكل صممية كانت ستسبب سلوكاً خاطئاً في الإنتاج:

| # | الثغرة | المكان | الإصلاح |
|---|--------|--------|---------|
| 1 | حالة المهمة كانت تُكتب كسلسلة حرفية `'in_progress'` لا تتطابق مع اسم `TaskStatus.inProgress`، فتعود القراءة كـ `scheduled` (حالة كاذبة) | `family_tasks_repository.dart` | استخدام `TaskStatus.inProgress.name` |
| 2 | التحقق من إتمام المهمة (verify) كان يرفض المهمة بعد إكمال أول طفل، ما يجعل المهام متعددة الأطفال غير قابلة للإغلاق | `family_tasks_repository.dart` | الحارس يرفض فقط المهمة الملغاة، وبوابة الفتح تقرأ سجل الإتمام الصادق لا حقل الحالة |
| 3 | تصادم مفتاح تفرد outbox (`idempotency_key`) عند حدوث حدثين في نفس الملّي ثانية (إكمال طفلَين، toggle متتالٍ) | `family_tasks_repository.dart` و`family_rewards_repository.dart` | إدراج الطابع الزمني في مفتاح التفرد |

## 2. النظام FS-007 — المهام والجداول اليومية

### 2.1 الشاشات الثماني (TK-001 إلى TK-008)

| المعرف | الشاشة | المسار |
|--------|--------|--------|
| TK-001 | لوحة المهام (الرئيسية) | `/tasks/:familyId` |
| TK-002 | إنشاء مهمة جديدة | `/tasks/:familyId/new` |
| TK-003 | تفاصيل المهمة | `/tasks/:familyId/detail/:taskId` |
| TK-004 | تعديل المهمة | `/tasks/:familyId/edit/:taskId` |
| TK-005 | سجل الإتمام (الصدق) | `/tasks/:familyId/log` |
| TK-006 | مهام الطفل | `/tasks/:familyId/child/:childId` |
| TK-007 | بوابة الإتمام (طلب/تأكيد) | `/tasks/:familyId/gate/:taskId` |
| TK-008 | الجدول الزمني اليومي | `/tasks/:familyId/timeline` |

جميع الشاشات مبنية على المكونات التسعة الأساسية (GuardianPrimitives)، بخط Cairo، وبألوان العلامة (كحلي #0F2A5B / تركواز #00B8A9)، وببطاقات Material 3 مستديرة الزوايا، وبحالات صادقة كاملة (تحميل / فارغ / خطأ / بدون صلاحية)، ومرفق فيها صورة العلامة `family_tasks.png` داخل `ClipRRect` بزاوية 16.

### 2.2 النمذجة والصدق (Honesty Contract)

- **سجل الإتمام هو مصدر الحقيقة:** حالة المهمة مشتقة وليست قابلة للكتابة مباشرة؛ لا توجد مهمة «مكتملة» إلا بوجود صف `completed` في السجل.
- **طفل يطلب → وليّ الأمر يؤكد:** `requestCompletion` يكتب `requested` ويحوله المهمة إلى `inProgress`؛ `verifyCompletion` هو الطريق الوحيد لحالة `completed`؛ `declineCompletion` يسجل الرفض دون تغيير الحالة.
- **الجسور مع FS-011:** حقل `linked_task_id` في `family_rules` (أُضيف في ترحيل قاعدة البيانات 24 مع ضمان التكرارية عبر `PRAGMA table_info`)، ودالة `TaskGateResolver` النقية تقرأ السجل الصادق (`completedChildren` / `gateCompletions`) لتوليد حكم قاعدة `taskGated`.
- **الصلاحيات:** `viewTasks` (ولي الأمر + الزوج/الزوجة + الطفل لمهامه) و`manageTasks` (ولي الأمر فقط) — عبر `FamilyRuntimeContext.can()` حصراً.

### 2.3 عقد التكرار السحابي (Outbox)

عمليات: `create` / `update` / `cancel` / `completion-requested` / `completed` / `completion-declined` — كل عملية صف كامل بحمولة JSON في جدول `outbox` بمفتاح تفرد، و`firestore_contracts.dart` يحوّلها إلى أحداث `family.task.*`.

## 3. النظام FS-008 — النقاط والمكافآت

### 3.1 الشاشات السبع (RW-001 إلى RW-007)

| المعرف | الشاشة | المسار |
|--------|--------|--------|
| RW-001 | لوحة النقاط والمكافآت | `/rewards/:familyId` |
| RW-002 | كتالوج المكافآت | `/rewards/:familyId` (القائمة) |
| RW-003 | محرر المكافأة (جديد/تعديل) | `/rewards/:familyId/new` و`/edit/:rewardId` |
| RW-004 | تفاصيل المكافأة | `/rewards/:familyId/detail/:rewardId` |
| RW-005 | المطالبات المعلّقة (موافقات الوالدين) | `/rewards/:familyId/claims` |
| RW-006 | سجل النقاط | `/rewards/:familyId/ledger/:childId` |
| RW-007 | أتمتة المنح | `/rewards/:familyId/automation` |

مرفق فيها صورة العلامة `family_rewards.png` داخل `ClipRRect` بزاوية 16 في الحالات الفارغة.

### 3.2 عقد الصدق المالي (Ledger Honesty)

- **الرصيد = مجموع `delta` حصراً:** لا يوجد عمود رصيد قابل للكتابة في أي مكان؛ دالة `balanceFor` تحسب `SUM(delta)` من سجل النقاط دائماً، فلا يمكن أن «ينجرف» الرصيد أو يكذب.
- **الطريق الوحيد للإنفاق = قرار ولي الأمر:** لا يدخل أي سطر سالب في السجل إلا عبر `approveClaim` بعد قرار موافقة صريح؛ `requestRedemption` فقط ينشئ مطالبة معلّقة؛ والمطالبات على مكافأة معطلة تُرفض صراحة (`reward_disabled:...`)؛ والقرار المزدوج مرفوض (`claim_already_decided:...`)؛ والإلغاء يتم دون أي حركة في السجل.
- **حماية الاستنزاف:** محاولة خصم يتجاوز الرصيد ترمي خطأ صراحة (`reward_balance_underflow:...`) — لا نجاح كاذب أبداً.

### 3.3 عقد التكرار السحابي

عمليات المكافآت: `create` / `update` / `toggle` — سجل النقاط: `earned` / `spent` — المطالبات (نوع مجمع مستقل `family_claim`): `requested` / `decided`. محوّلة في `firestore_contracts.dart` إلى أحداث `family.reward.*`.

## 7. الترابط مع المراحل الأخرى

- **FS-011 قواعد العائلة:** جسر ثنائي الاتجاه — قاعدة `taskGated` تقرأ سجل الإتمام الصادق لفتح البوابات (مثل فتح تطبيق بعد إتمام الواجب)، وقاعدة `rewardUnlocked` تتكامل مع أتمتة المنح التلقائي للنقاط.
- **FS-005 الأنماط المخصصة / FS-015 ربط الأجهزة:** أذونات `viewTasks/manageTasks/viewRewards/manageRewards` مؤطرة في مصفوفات التفويض الموحدة، وتُعرَض مجموعات المهام والمكافآت في لوحة العائلة ضمن أزرار مقيّدة بالصلاحيات.
- **المزامنة:** كل طفرات FS-007/FS-008 تمر بجدول `outbox` بنفس صيغة المراحل السابقة دون أي تغيير على مخطط `outbox` أو قواعد Firebase أو خادم Render.
