# Policy Enforcement Model

## Resolution order

The pure resolver applies the following order for a scoped child device:

1. A `revoked` device produces `DEVICE_REVOKED` before policy evaluation.
2. A missing policy snapshot, required-version gap, or over-age snapshot produces `POLICY_STALE`.
3. A valid active temporary override is evaluated before a scheduled policy and can produce `TEMPORARY_ALLOW`.
4. Enabled matching policies are filtered by time and target, then highest priority wins deterministically.
5. No matching active policy produces `ALLOW`; a matching policy produces `RESTRICT` intent.

`offline` does not itself discard valid locally stored policy. It becomes `POLICY_STALE` only when the stored validity boundary is exceeded or a known minimum version is unavailable.

## Decision versus Android action

| Output | Domain meaning | Android Phase 14 meaning |
|---|---|---|
| `allow` | No active restriction intent. | No platform action requested. |
| `warn` | Future observation capability may provide warning-only experience. | Not generated by baseline resolver. |
| `restrict` | Policy requests restriction. | Adapter returns unsupported/blocked until a verified Android mechanism exists. |
| `bedtime` | Reserved for future policy semantic type. | Not generated from a name or a guessed schedule. |
| `temporaryAllow` | A valid delivered override allows the target temporarily. | No platform action requested. |
| `noEnforcement` | State is suspended or no action is requested. | No platform action requested. |
| `policyStale` | Local policy cannot safely satisfy a known freshness/version requirement. | No platform action claimed. |
| `deviceRevoked` | Device is locally revoked. | No platform action claimed; status must be surfaced. |

## Version integrity and idempotency

Policy deliveries compare `(deviceId, policyId, version)`. An older version is ignored, an equal version with equivalent payload is idempotent, and only a newer version replaces the local snapshot. Delivery writes, state watermark changes, and status event queueing occur in one SQLite transaction.

## Override delivery limitation

The resolver supports a local override type for deterministic testing and future server-mediated delivery. Existing Firestore rules intentionally restrict remote override reads to parents. Therefore the child application must not read parent-only override documents directly and must not pretend it has a temporary override until a permitted delivery path is implemented and verified.
